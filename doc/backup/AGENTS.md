# 通用项目规则

## 规则的规则

- **不要静默修改**：认为某条规则不合适，说明哪一条、建议改成什么、为什么。用户明确要求改某份规则、或批准了你提出的方案，才改对应规则。

## 文档与沟通规则 (适用于写文档、输出回复、规则、代码注释等)

- 保证专业且正确，同时把事情讲清楚。必须要让非专业人也能看得懂，也能理解专业内容。所以不要只甩一堆术语，要好好想这样用术语非专业人能不能看懂。直接讲事情本身，不要乱用比喻。在把事情讲清楚的前提下，写得越简单越好。
- 开发或修改代码时，行为变了同一轮维护更新文档，不要留下过时文档。
- 文档要能**续工**（以后接得上决策）和**学习**（留下知识和经验，让用户看完能学懂这个项目）。

## 代码质量与最佳实践规则

- 按**真人开发团队认真维护**的标准开发，注重代码可读性。不要图省事、赶工、假扩展性留下长期债。开发过程遵循工程最佳实践。**先探索，后规划，最后编码**。
- **废除历史包袱 (No Backward Compatibility)**，不保留过时、废弃或无效的代码。直接删除旧实现，禁止编写兼容层（Compatibility Layers）、迁移脚本（Migration Scripts）或退化备选逻辑（Fallbacks）。
- **奥卡姆剃刀原则 (KISS & Anti-Over-Engineering)**：仅选择满足当前确切需求的最简实现。严禁过早抽象、泛化接口或设计不必要的配置层。
- **高内聚低耦合 (Modularization & Separation of Concerns)**，维持模块的自治与单一职责，界限清晰，职责明确。代码用文件夹合理组织。
- **渐进式分层构建 (Incremental Building)**，优先构建并跑通最小化端到端（End-to-End）闭环，在此基础上迭代扩展。严禁为了推倒重构而破坏已稳定的现有功能。
- **充分挖掘现有依赖 (Maximize Existing Dependencies)**，在引入新依赖或手动编写新逻辑前，必须先全面评估当前项目已有依赖的功能库。严禁在未确认现有库能力前盲目引入新包。
- **长远架构视野 (Long-Term Architectural Decisions)**，所有架构设计必须面向长期稳定维护。严禁引入“后续再替换/临时凑合”的半成品方案。
- **拥抱成熟生态 (Prioritize Mature Libraries)**，优先选择社区活跃、维护良好的成熟开源库。除非有不可替代的核心痛点或性能瓶颈，否则绝不手造轮子。
- **参考业界成熟作法，先对标，再动手 (Adopt Proven Patterns)**：多数要做的东西业界早有同类、规矩早定过（语言与标准组织的规范、协议与文件格式、某个库或 API 的既定语义、系统与运行时的实际约束、同类成熟产品的通行做法）。动手前先查规范原文，外加至少一个成熟实现，结论写进代码注释或文档：有对标就写出处「来源名 + 章节 / 文件」；与默认行为不一致就算有意偏离，要写明偏离了哪条、为什么；查不到可对标东西的**不许编造出处**，改写「查过哪些来源、没找到什么、为什么只能自研」，并先说一声再动手。判据是**有没有留下检索记录**，不是有没有引经据典。这条只挡没查就写、写完补引用、凭空发明未经验证的复杂模式，不禁止说明过的自研。

## UI/UX 规则

- **操作必须有反馈**：用户触发的操作须有可感知反馈（跟手进度、状态变化、短提示、达阈值才提交等），否则无法区分没点上、点上了没执行、执行错了。手势应对齐「进行中可见、完成可辨」；禁止静默无反应。

## 功能文档记录规则（`doc/架构-功能-实现/`）

目录名即文档结构：**架构 → 功能 → 实现**。架构的唯一出口是 `00-总览与分层.md`；编号文档每个 = 一个功能，整篇**先功能后实现**：

- **功能段（写在最前）**：用用户语言写，用户也能看懂——这个功能在软件里能干什么、行为是什么（提示文案、默认值、保存去向、失败怎样报错、「故意没有什么」与例外）。同一用户操作背后若是不同处理路径（如普通下载 vs 嗅探合并下载），每条都写清；这一层不写模块名类名。
- **实现段（其后）**：对应每个功能的实现及不属于用户可见功能的其他实现。写清这个能力**怎么来的、为什么长这样**，不只是文件清单。让读者带走「换项目也还记得」的那一层：这类系统通常怎么分层、关键生命周期/接缝在哪、有哪些成熟做法、我们选了什么、故意不做什么。固定这几节（节名可微调，内容别空）：

1. **意图与边界** — 要解决什么；明确不做什么。
2. **怎么做成的** — 关键决策与实现路径（为何先 A 后 B、踩过哪些弯路后定案）；不是聊天流水账。
3. **对标来源**（必填） — 有对标就写出处「来源名 + 章节 / 文件」；查不到就写「查过哪些来源、没找到什么、为什么只能自研」；有意偏离就写偏离了哪条、为什么。**缺的是检索记录，不是引经据典。**
4. **结构与接缝** — 模块怎么分、改动从哪进；用大白话标出值得长期记住的概念。
5. **设计取舍** — 为什么这条路，而不是更「完整」或更省事的路。
6. **行为契约**（若有） — 例如鼠标/触摸是否同一套；什么情况下不要做某事。
7. **经验入口** — 值得留下的教训；细节链到 `doc/值得记住的坑/`，此处写要点即可（勿复制整套三行式）。
8. **以后改时先看** — 三条以内的硬约束。

## 踩坑归档规则

当检测到解决重大 Bug、排查复杂问题或完成关键技术踩坑后，严格按照项目约定，将具备长期复用价值的经验自动归档至项目本地的踩坑知识库中。

- 坑记在当前仓库 `doc/值得记住的坑/`。目录不存在就新建。文件名以项目名命名。
- 每条三行式 **现象 → 原因 → 做法**。**现象**：当时看起来是什么样。**原因**：为什么会这样。**做法**：可复用的一般规则，不只是这次的补丁。
- 语言简练，直击要害，杜绝推导过程等无意义废话。
