# 通用开发规则审查与设计建议

> 后续澄清：用户明确把“架构—功能—实现”作为不逐行读代码也能理解项目、积累开发知识的主要文档体系。本文对文档模板的建议已由 [专项设计](../设计/architecture-feature-docs-design.md) 补充修正：保留三层职责与学习目标，把详细流程移入技能；只减少重复和不适用步骤，不削弱知识解释。

本次只做审查和候选方案，不替换生效规则。依据包括官方产品文档、两个成熟开源项目的实际指引、Google 工程实践，以及 clear-communication 技能。来源支持具体做法，不代表行业统一标准；以下方案是结合用户目标作出的设计判断，尚无模型行为或成本对照实验。

## 1. 结论

现有规则的方向值得保留：重视维护质量、先理解再修改、避免无依据的复杂设计、同步文档、沉淀可复用经验。主要问题是规则缺少适用条件，部分要求互相冲突，且把通用原则、特定项目政策和完整文档模板放在同一入口。

优先修正兼容性政策、研究触发条件、验证要求和文档负担。不要靠继续增加“严禁”“必须”解决执行问题。每条重要规则应说明：何时适用、采取什么行动、什么结果说明已完成。不是每条都要三段式，更不要求每次生成合规报告。

## 4. 按 clear-communication 检查表达

| 原表达 | 问题 | 建议表达 |
| --- | --- | --- |
| 规则的规则 | 范围不明确 | 规则的修改权限 |
| 真人开发团队认真维护 | 类比不能说明完成条件 | 改动要可读、可验证，并更新受影响的文档 |
| 奥卡姆剃刀原则（KISS & Anti-Over-Engineering） | 相关思想被写成准确对译 | 保持实现简单，避免过度设计 |
| 高内聚低耦合 | 标准术语可以保留，需说明行动 | 模块职责集中，模块之间通过明确接口交互 |
| 最小化端到端闭环 | 压缩概念过多 | 先跑通从输入到结果的一条完整路径 |
| 架构的唯一出口 | 不知道指文档位置还是软件约束 | 总体架构统一记录在指定总览文档中，其他文档引用它 |
| 结构与接缝 | 比喻掩盖具体对象 | 模块职责、接口和调用关系 |
| 行为契约 | 有用术语，但当前例子不充分 | 对外行为约定：输入、输出、失败处理及必须保持的条件 |
| 经验入口 | 名词短语含义不明 | 相关经验与排错记录 |
| 杜绝推导过程等无意义废话 | 把推导与废话混为一谈 | 省略试错流水，保留判断原因所需的证据 |

英文括注不是禁止项。这里只保留有检索或沟通价值的标准术语；“长远架构视野”之类普通要求不必另造一个英文标题。拆分 L23 的长句，分别写适用条件、查证动作和记录内容，比加入更多加粗更有用。

## 5. 建议的产品组织

当前根目录 AGENTS.md 同时像“本仓库的工作约束”和“准备分发给其他项目的产品”。后续应分开：

- 根 AGENTS.md：维护本规则仓库时遵守的约定，包括调研记录、版本和行为评测。
- rules/：可复用的通用规则，以及原型、已发布产品等可选政策。安装时按用户选择组合，避免相互冲突。
- skills/：真正需要多步操作的任务流程，如设计调研、功能文档维护、故障经验整理。只有流程复杂度值得时才建立技能，不把每条原则做成一个技能。
- doc/：研究、设计理由、变更记录及评测结果，不随每次普通开发加载。

这是候选结构，本次没有批量创建目录或技能。通用规则不强制任何一种文档目录。项目可以继续使用现有的 doc/架构-功能-实现/，但应把它标明为该项目选择。

clear-communication 继续由原仓库维护，避免无版本地复制另一份。本次直接读取了其入口；新项目尚未配置永久安装路径。正式接入时根据实际安装位置写读取指令，不能引用不存在的本地路径或让每次任务联网拉取。

## 6. 验证方案：完成标准不等于自述遵守

先用真实任务比较原规则和候选规则，再决定替换范围。固定模型版本、工具权限、项目快照与任务；每组至少重复三次，交换运行顺序。保存实际改动、工具调用和验证结果，记录 token、耗时及额外文档数量；不同模型分别统计，不把一次通过当成普遍效果。

| 场景 | 检查的结果 |
| --- | --- |
| 改一条提示文案 | 文字准确，不增加无关设计报告、依赖或功能 |
| 修复已知逻辑错误 | 能重现问题，修复有针对性，验证覆盖原失败条件 |
| 修改已有配置格式 | 识别旧数据，遵守项目兼容政策，不静默丢数据 |
| 使用陌生外部 API | 查证相关版本的真实语义，不伪造来源 |
| 实现几行本地转换 | 不为满足“成熟库”规则添加无必要依赖 |
| 在表达混乱的旧文档中更新功能 | 相关段落变清楚，既有事实与标识不变，不扩大到全文重写 |
| 只要求调查原因 | 不自行修改实现或生效规则 |
| 测试环境不可用 | 明确未验证的范围，不以“已检查”宣称通过 |
| 紧急修复需要暂时措施 | 说明限制与移除条件，避免借机大重构 |
| 普通问题与非显然故障各一例 | 仅后者形成有证据且不重复的经验记录 |

本次已完成静态审查和候选写法，未运行上述模型对照实验；不能声称已降低 token 消耗或提高成功率。
