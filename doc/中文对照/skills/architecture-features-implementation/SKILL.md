# 架构—功能—实现

让读者不逐行读代码也能理解软件全貌、设计与可复用知识。代理必须查看相关实现和验证依据，不能以流畅解释代替事实。遵循项目语言与已有文档位置；无约定时使用 `doc/架构-功能-实现/`。

## 选择工作范围

- **日常维护：** 复用本次任务已读取的文件、需求与验证结果，定位受影响的段落。只有相关事实、解释或导航改变才更新。没有文档影响时结束，不额外生成报告。
- **创建或实质改写页面：** 读取 [内容与示例](references/document-shapes.md)，选择对应层次，不把问题清单机械变成固定章节。
- **首次建立或明确授权的全面整理：** 再读取 [首次建档](references/initial-documentation.md)。普通代码维护、阅读旧文档或发现缺页，不代表授权整库整理。

当前上下文已有适用内容时复用，不重复加载。只读所需资源；本技能不规定内部思考格式，也不要求写提纲、自检表或额外计划文件。

## 三层职责

| 层次 | 必须让读者理解 | 更新时机 |
| --- | --- | --- |
| 架构 | 系统边界、主要职责与协作、关键数据流、核心选择如何回应约束 | 系统结构、共享机制或关键决策变化 |
| 功能 | 完整能力范围；相关功能的输入、结果、重要默认和失败行为 | 能力增删、对外行为变化 |
| 实现 | 关键执行路径、难点、机制与取舍、验证依据及维护入口 | 机制、约束或重要设计理由变化 |

总体架构集中说明并链接专题。功能页先功能、后实现；共享知识只解释一次。功能按使用者目标组织，不按每个按钮或代码文件拆篇。已有等价结构优先复用。

这些页面描述当前支持版本。预期行为和未实现方案写入已有需求或任务记录；日期流水、旧实现经过与被替代决定写入项目开发日志或既有决策记录，默认位置为 `doc/开发日志/`。当前文档保留解释现状必要的理由与限制，可链接历史，但不堆积演变记录。无需为此安装日志技能或迁移无关旧文档。

## 执行

### 1. 确定依据和受影响内容

对照任务目标、相关文档、代码、配置和已有验证，区分已实现、计划与未知。只读取解决当前不确定性所需的材料。记录位置与依据可留在当前工作上下文，不另建台账。

文档与代码不一致时，先判断是实现未满足要求还是说明过时。依据用户要求、适用约定与实际行为处理；无法判定的重要冲突明确提出，不默默改代码迎合文档，也不把缺陷改写成正确行为。文档任务本身不授权修改产品代码。

### 2. 写行为、机制与值得积累的知识

先写读者能观察到的行为，再解释关键路径和选择。把具体约束、机制、作用、代价及适用条件连起来；简单事实不硬凑经验或替代方案。必要术语在当前场景中解释，随后一致复用。

从代码只能确认机制，不能据此编造历史动机。无决策记录时说明理由未知，或明确这是基于现状的分析。外部规范与陌生机制按需查一手资料，记录真正支持结论的来源，不给每项普通实现凑引用。

正文应能独立理解，代码链接供核验和维护，不代替解释。链接优先用相对路径和稳定名称，必要时指出符号名；不贴大段代码、命令输出、敏感信息或聊天流水。关键验证说明覆盖了什么、尚未覆盖什么，不将未运行测试写为通过。

只改本次涉及的完整段落及必要相邻内容，保留准确术语、标识与有效解释。总体决策改变时更新当前说明；值得保留的旧决策在日志或既有历史记录中标为已替代并链接新决定，不在当前页面继续展示旧方案，也不把历史重写成从来如此。

### 3. 核对本次改动并交付

- 行为、数值、默认、失败处理与依据相符；计划没有冒充现状，未知没有被润色成事实。
- 受影响的总览、索引、功能页、共享说明和图示一致，链接可用；无关内容未被顺带重写。
- 读者能说明涉及的部分如何协作、为什么这样选择，以及重要限制；正文不要求先阅读源码。

定点修正具体缺陷后结束。交付简述文档变更和必要未知，复用任务本身的进展与结论，不重复附自检报告。若范围较大，分批完成全部授权内容；受阻时明确剩余范围。


语言约定：按用户指定语言输出，否则沿用对话或项目既有语言；英文指令不要求英文或双语输出。保留已有路径和标识，不因切换语言重命名。
