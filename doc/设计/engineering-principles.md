# 通用规则的总原则与工程依据

日期：2026-10-28。对应版本：0.2.0。用户要求明确两个总目标，并用可执行规则支持它们：达到认真维护项目的团队标准；遵循适用规范与成熟实践，避免凭想象实现。

## 研究与取舍

| 一手来源 | 支持的做法 | 本规则如何采用 |
| --- | --- | --- |
| [Google：代码审查标准](https://google.github.io/eng-practices/review/reviewer/standard.html) | 持续改善代码整体质量，事实优先于偏好；不因追求完美阻碍合理改进 | 以维护结果定义团队标准，不复制全部团队流程，不无限润色 |
| [Google：审查关注点](https://google.github.io/eng-practices/review/reviewer/looking-for.html) | 设计、行为、复杂度、边界、测试和注释均影响质量 | 加入与改动相关的边界和失败路径，交付前从维护者角度检查 |
| [Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/master/0000-template.md) | 说明动机、具体行为、取舍与已有经验；存在先例本身不足以证明方案合理 | 研究成熟实现的条件与代价，不以“别人也这么做”为结论；不要求普通修改填写整份 RFC |
| [Python PEP 1](https://peps.python.org/pep-0001/) | 设计提案承担规范与理由记录；多数增强和缺陷修复无需 PEP | 区分重要决策记录与日常工作，避免每次都增加设计文件 |
| [GitHub：自定义指令](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions) | 指令宜简短明确且作用范围适当，模型不保证每次完全遵守 | 保持通用要求可复用，项目补充真实命令与具体约束；文本规则不能代替工具验证 |

访问日期均为 2026-10-28。这些资料是各自组织的公开实践，不能代表所有领域的统一标准，也不是本规则效果的对照实验。下述跨领域组织方式为本项目设计判断。

## 总原则与行动的对应关系

“认真维护”不是模仿人数、会议和审批，而是对可使用、可验证、可维护、可交接的结果负责。“成熟实践”不是迷信流行库，而是理解已有方案为什么成立、哪些边界容易出错，并据此实施。

| 目标 | 原有缺口 | 本次补充的行为与可观察结果 |
| --- | --- | --- |
| 团队维护质量 | “先理解再修改”没有明确完成依据 | 动手前明确预期行为和验收方式，复用任务说明，不强制新文件 |
| 团队维护质量 | 只要求处理错误，未提示识别隐蔽路径 | 按实际机制检查输入、资源、超时、重复执行、并发或中断风险，保留相关验证 |
| 团队维护质量 | 验证可能只检查正常流程 | 检查相关边界与失败，并从维护者角度审视实际差异；不因风格偏好扩大范围 |
| 遵循标准 | 只在自认陌生时查询，可能漏掉已有约定 | 设计前识别是否受规范约束，核对版本与环境，未知关键语义不可猜测 |
| 遵循标准 | 混淆规范、库行为和参考实现 | 指明证据类别，实际冲突要解释；参考实现不能替代规范 |
| 借鉴成熟方法 | “优先现有依赖”只解决选库，不保证正确使用 | 理解成熟方案的条件、失败处理和代价，再选择或偏离 |
| 控制负担 | 检索有起点却没有终点 | 约束、关键行为与验证方法足够支持实现时结束；影响方案的未知不能略过 |

## 证据和验证如何搭配

正式标准规定互操作要求，官方库文档说明所用版本的约定，参考实现提供落地经验，实验揭示特定环境的行为。它们解决的问题不同，不能机械排成一个覆盖所有情况的可信度榜单。

例如，规范描述预期行为，而实际运行出现差异时，不能仅凭实验就断定规范无效，也不能忽视差异继续开发。需要查版本、适用范围和已知限制，说明项目将如何处理。若有意不支持某项要求，应明确支持范围，不能笼统宣称完全兼容。

验证也不能只让自己生成的数据通过自己写的解析器。对于互操作行为，需要使用适用的独立样例、约定测试或真实对接来检查边界。这是从总目标导出的规则设计，不是本次已经执行了各领域的合规测试。

## 成本与适用边界

小修改仍应识别相关约束，但通常可复用项目已有结论，无需重新联网。涉及不熟悉或易错的外部机制时加深查证，关键设计才保留来源与取舍。没有规定每次读取多少文件、引用几个来源或生成几份报告。

保留原有任务范围、兼容政策、用户授权、文档学习和沟通规则。这两个总目标提供方向，不替代其他工作约定。未添加新技能；现阶段通用规则即可表达这些要求，独立流程是否值得封装应由真实重复任务决定。

## 验证状态与后续场景

本次完成来源核对、规则修订和静态检查，未运行独立代理实验。以下为后续行为评测的任务与判据，不是已通过结果：

| 任务 | 应观察到的行为 |
| --- | --- |
| 按现有组件改一条提示 | 复用已知约定，不写研究报告或顺带重构 |
| 实现带正式规范的文件读写 | 核对适用版本与要求，用独立样例验证，不仅自写自读 |
| 增加网络请求重试 | 核查对应协议和客户端约定，处理实际相关的重复执行、超时与失败情况 |
| 参考库行为与规范不一致 | 明确差异和支持范围，不把参考库行为直接称为标准 |
| 没有现成组件满足特殊约束 | 用事实解释限制，合理自研并验证，不因允许自研而臆造语义 |
| 修复小问题时发现无关技术债 | 完成本次修复，记录确有必要的问题，不借“专业质量”全面重构 |

正式评测应保存任务、实际输出与工具行为，并比较正确性、额外工作、耗时及 token。静态检查和作者推演均不能证明这些目标已经实现。
