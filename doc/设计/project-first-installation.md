# 项目优先的规则与技能安装

日期：2026-10-28。目标：规则、技能和启用要求随项目版本管理，同时兼容不同代理的加载机制。此文是安装设计与官方资料核对，不是跨客户端实测报告。

## 1. 三件事分开判断

- **归属范围**：哪些项目需要遵守规则、使用哪个技能版本。这决定内容属于项目还是个人。
- **文件发现位置**：宿主从哪个目录、配置或账号取得技能。这是加载机制，不决定规则应该影响哪些项目。
- **激活要求**：什么时候必须读取规则或使用技能。技能可发现不等于每次触发，激活约定需要写进实际生效的项目或个人指引。

因此，技能因为某种限制被放到个人目录时，项目的“何时使用”规则仍应属于该项目，不能顺手写成影响所有项目的个人政策。反过来，用户明确希望跨项目使用清晰沟通时，才适合个人安装和个人触发约定。

## 2. 官方支持核对

| 宿主与适用环境 | 项目技能位置 | 项目规则及需注意的边界 |
| --- | --- | --- |
| Codex 本地仓库工作流 | `.agents/skills/` | 项目 AGENTS.md；同名技能不自动合并，需检查实际来源。[官方技能说明](https://learn.chatgpt.com/docs/build-skills) |
| Claude Code 仓库会话 | `.claude/skills/` | CLAUDE.md；新版对 AGENTS.md 的读取与版本、现有 CLAUDE.md 和配置有关。兼容入口可使用官方支持的 `@AGENTS.md` 导入。[技能](https://code.claude.com/docs/en/skills)、[规则与导入](https://code.claude.com/docs/en/memory) |
| Cursor 本地项目 | `.agents/skills/` 或 `.cursor/skills/`，并有兼容位置 | 项目 Rules 可设持续适用，按实际版本选择入口。[技能](https://cursor.com/help/customization/skills)、[规则](https://cursor.com/help/customization/rules) |
| VS Code 中的 Copilot | Copilot harness 文档列 `.github/skills/`；其他执行方式列有更多兼容位置 | 先确定实际 harness（执行代理的宿主组件），不能把某模式的兼容目录推广到全部 Copilot 客户端。[VS Code 技能说明](https://code.visualstudio.com/docs/agent-customization/agent-skills) |

均为 2026-10-28 阅读官方页面所得。网页能力不等于用户安装版本必然支持。Claude 官方还区分仓库会话、Cowork 与项目云端线程；本机个人技能不可据此假定云端可见。其他代理的远程、容器、审查功能也必须分别核验，不承诺“一次本地安装、所有环境生效”。

## 3. 最推荐的做法

**项目专用或影响项目结果的规则、完整技能包、触发约定和可移植安装记录，全部随项目保存。不同代理只增加必要的加载入口。** 项目中不只留上游链接：安装时获取选中版本的完整文件，使以后克隆项目不必重新下载才能使用。引用外部源码时保留适用许可证与来源；无权纳入仓库时保留来源和安装步骤，并如实说明并非完整随库分发。

规则集中在 `.agent-rules/agent-rules-and-skills/`。技能通常放在主要宿主支持的项目目录；以 Codex 为主可用 `.agents/skills/`，以 Claude Code 为主可用 `.claude/skills/`。已有正确位置时沿用，不为了目录统一搬动或复制。

这是“一份维护来源＋必要适配入口”，不是要求所有代理原生识别同一个目录。一个项目只使用一个代理时，只配置这个代理；多代理项目明确需要支持哪些宿主，不自动生成全平台配置。

对于同一技能，多代理优先共享宿主都能读取的同一份。共同发现目录不存在时，纯文本技能可由项目指引明确读取同一包，并注明没有原生技能发现保证。确实需要各自的原生调用入口时，再按许可建立可追踪的同步副本；锁定同一来源版本，不独立维护，并检查任何一个宿主是否因此重复发现两份技能。不能解决重复或遮蔽时，不宣称兼容完成。

不要默认用符号链接解决跨目录问题。Windows 权限、Git 检出方式和远程环境可能使链接失效；仅在团队环境支持且验证后使用。

## 4. 不支持时的处理顺序

| 实际能力 | 处理 | 必须报告的限制 |
| --- | --- | --- |
| 原生支持项目规则与项目技能 | 完整内容存项目，配置实际入口并验证 | 发现、可调用、默认触发分别确认 |
| 不发现该目录，但允许配置项目技能路径 | 使用正式支持的路径配置 | 换环境后配置是否仍有效 |
| 无原生技能，但可读项目文件和项目指引 | 纯文本技能在项目保留，通过指引按需读取 | 是文件指令方式，不保证技能菜单、元数据、hooks 或特殊工具语义 |
| 只接受个人或账号技能，但允许项目规则 | 保留项目来源版本，说明限制后取得对应范围授权，安装个人或账号执行副本；项目触发仍留项目 | 本地副本不是项目可复现的全部保证，机器或账号需要单独配置 |
| 无法读取项目技能且不能写有效项目指引 | 给出该宿主支持的导入步骤或明确不支持 | 不能通过复制文件宣称已启用，不用个人全局规则偷偷替代 |

明确授权项目安装不等于授权个人或账号安装。已有授权覆盖时不重复询问。受管理员策略禁止的能力不能靠手动读取或改变位置绕过。

## 5. 版本、范围和同步

同名个人技能不能未经核对替代项目指定版本。不同代理的优先级不一致，显式选择项目路径也可能不改变原生命令的解析，须验证实际加载的文件。不擅自删除个人技能或改其名称来消除冲突，必要时说明待处理项。

共享安装记录保存来源提交、项目相对路径、归属、宿主适配方式和验证状态。机器绝对路径、账号标识和本地绑定另存不提交的本地记录；共享记录只说明需要哪种本地前置条件，不能将他人的主目录当成可移植路径。

切换工作树、远端或容器后，项目文件应在当前检出版本可见；检查是否被忽略、是否确实提交、是否被权限限制。项目文件没有自动提交：安装者只检查并报告，不因安装技能擅自 git add、提交或推送。

更新以项目选定版本为准，不因为上游 main 变化就静默替换。个人执行副本、同步副本或导入包需要单独核对版本；只能检查到的环境报告已验证，其余标为待验证。

## 6. 对现有流程的修正与测试状态

原流程已有项目范围和替代读取的概念，但没有充分区分归属与发现位置，也未规定个人版本复用、多宿主副本、云端边界和本地绑定分离。本次将以上决策加入 INSTALL.md，不改变已有项目的实际安装。

之前的临时项目演练只证明本地文件组合和重复执行，不证明这里列出的所有宿主模式。新增设计尚待在单宿主、多宿主、个人版本冲突和云端不可见场景中分别实测，不能以来源核对代替行为验证。

## 唯一真源的澄清

本文的项目内“维护来源”仅指派生文件的保存与同步位置。内容权威始终是用户选定的真源仓库，按 [唯一真源设计](single-source-maintenance.md) 和 [同步协议](../../SYNC.md) 比对与汇回；不允许各项目自行演变正文。本节优先于早期可能产生歧义的措辞。
