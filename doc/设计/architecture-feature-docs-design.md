# 架构—功能—实现文档：研究与规则、技能设计

日期：2026-10-28。设计阶段记录；用户后续授权实施，0.1.0 已创建仓库内技能并更新本仓库规则，见 [变更记录](../开发日志/CHANGELOG.md)。以下方案保留为决策依据，其中“待采用”等表述描述设计时状态。未进行个人全局安装。

## 1. 目标与对上一轮审查的修正

用户主要通过代理完成开发，希望无需逐行阅读代码，也能掌握项目的整体结构、功能范围、重要设计与经验。文档因此既是开发与验收依据，也是长期学习材料。减少代理负担仍然重要，但不能以此为由删掉解释设计和沉淀知识的内容。

上一轮审查把固定文档结构主要视为通用规则的额外负担，未充分体现这一用途。修正为：保留“架构—功能—实现”作为用户明确选择的文档体系，把详细写作流程交给技能。压缩重复和机械步骤，不压缩理解所必需的内容。

用户可以通过文档理解与决策，代理仍需核对代码、配置及测试。文档是面向人的说明和开发约定，不是证明运行行为正确的唯一依据。文档与代码冲突时，先区分“约定尚未实现”和“说明已经过时”，不能自动选择一方或修改代码来迎合文档。

## 2. 调研依据与取舍

| 一手来源 | 可借鉴的内容 | 本方案的取舍 |
| --- | --- | --- |
| [C4：Diagrams](https://c4model.com/diagrams) | 用不同层次的图服务不同读者，并非所有项目都需要全部层次 | 保留总体视图，必要时增加局部图；不默认画类图，也不把三层文档声称为 C4 标准 |
| [arc42：Solution Strategy](https://docs.arc42.org/section-4/) | 核心方案应解释如何回应目标与约束，详细内容另行展开 | 架构不只罗列技术栈；说明为何划分职责、如何满足关键要求 |
| [arc42：Method](https://arc42.org/method/) | 文档、设计、实现和评价持续反馈；实施时核对实际结构与设计 | 开发前写必要意图，开发后用事实校正；避免一次写完长期不维护 |
| [Diátaxis：Explanation](https://diataxis.fr/explanation/) | 解释性文档以理解为目标，连接背景、原因和取舍，并保持主题边界 | 学习解释是正式交付的一部分；不把每篇都扩成操作教程或 API 手册 |
| [Michael Nygard：Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) | 记录重要决策的背景、选择和后果；被替代的决策保留历史并指向新决定 | 少量重要决定保留理由；跨功能或有重要演变历史时才独立成篇，不为每次修改创建记录 |

访问日期：2026-10-28。以上方法支持组织和维护设计，但不能证明本技能会提升长期记忆或节省 token。后者需要实际使用验证。本方案不是任一方法的完整实现，模板和例子为针对用户目标的设计。

## 3. 三层内容分别回答什么

| 阅读层次 | 读者应能回答的问题 | 应有内容 | 不应成为 |
| --- | --- | --- | --- |
| 架构 | 这个软件由哪些主要部分组成，如何配合，为什么这么分？换一个项目还能借鉴什么？ | 系统边界、主要职责、关键数据流、影响结构的约束、核心选择及适用条件 | 技术栈名单、目录树或大量类名 |
| 功能 | 软件完整地提供哪些能力？每项能力的输入、结果和重要限制是什么？重新开发时需要实现什么？ | 功能目录、典型场景、默认与失败行为、关键差异、已实现与计划状态 | 按代码模块罗列的文件清单，或逐像素操作手册 |
| 实现 | 该功能如何实现，难点在哪里，为什么选择这一方案，怎样知道它有效？ | 一条关键执行路径、必要机制、决策与代价、代码入口、验证依据、复用条件 | 逐行翻译代码、试错流水或只有文件链接的索引 |

三层是阅读深度，不要求三个目录。读者从架构或功能总览进入，只有需要时才深入实现。架构不是写完功能后的附录，而是独立的学习主线。

“功能全貌”按用户目标组织，例如“创建任务、管理任务、查看结果”，不按每个按钮拆篇。库和命令行工具也有使用者，其功能可以是调用、转换或构建能力。备份、更新、安全等只要影响使用或维护，也不能因为没有界面就遗漏。

## 4. 推荐文档组织

保留用户现有路径习惯。最小结构如下，已有项目沿用其相应页面，不强制改名迁移：

```text
doc/架构-功能-实现/
  00-总览与分层.md
  01-功能全貌.md
  02-某个功能.md
  03-另一个功能.md
```

- `00-总览与分层.md` 是总体架构的权威说明位置。内容较多时可以拆专题并链接，不要求把全部架构知识塞进一篇。包括系统用途和边界、主要部分及职责、关键流程、核心选择和限制，以及通往功能全貌的链接。
- `01-功能全貌.md` 是完整功能索引。每个功能用一句话说明用途，链接详细说明；存在尚未完成的功能时明确状态。已有 README 具备同样职责时可直接复用，不建立第二份重复清单。
- 编号功能文档前半篇写功能行为，后半篇写实现和理由。简单功能可合在同一篇，复杂功能可拆分；判断依据是能否独立理解与维护，不是文件数量。
- 跨功能共用机制在总览或独立专题中解释一次，各功能只写如何使用及特殊之处。真正需要时再创建共享专题目录。
- 已有 `doc/值得记住的坑/` 继续承载排错细节。功能或架构文档保留影响设计的结论与链接，不再复制完整记录。

不把每条历史决定都放在当前说明里。当前文档描述现状；需要保留的重要旧决策单独标明已被替代，并指向当前决定。读者不能把旧结论误读成当前要求。

## 5. 怎样写出能积累知识的内容

知识应从项目中的具体问题出发：遇到什么约束，采用什么机制，为什么有帮助，代价是什么，换到什么条件下仍适用。它是一条因果关系，而非每次必须填写的五个标题。

值得保留的内容通常会改变未来的判断，例如：为什么把耗时任务从界面进程分离；如何识别重复执行；什么情况下选择本地存储；如何从失败中恢复。偶发拼写错误或工具命令失误通常不值得提升成架构经验。

有用的术语要出现，并在首次需要时解释它在当前问题里的作用。允许适量领域背景，让读者逐渐掌握术语；不附无关百科。避免把当前选择讲成唯一正确方案。重要取舍要解释至少一个实际相关的代价或替代方案，但不硬凑对比数量。

### 示例：后台导出（虚构演示，不代表任何项目已经实现）

**架构说明：** 界面负责接收导出请求和显示状态，后台执行器负责生成文件。把生成过程分开，是因为导出时间可能较长，不能阻塞其他操作。任务状态存入数据库，使程序重启后仍能找到未完成任务。这种安排增加了任务状态和恢复逻辑的维护成本；如果导出始终很快且允许失败后重新开始，直接执行可能更简单。

**功能说明：** 用户提交导出后会得到一条任务记录，可继续使用软件并查看进度。成功后可以获取文件，失败时可查看原因并重试。对于这个示例设计，程序重启后会重新执行未完成任务；它并不承诺从上次进度继续。实现前应确认重试是否允许生成重复结果。

**实现与知识说明：** 执行器从待处理任务中领取工作，完成后保存结果并更新任务状态。如果程序在文件生成后、状态保存前退出，恢复后可能再次执行同一任务。因此需要确定重复执行的处理方式。让同一任务重复执行仍产生一致结果，称为幂等性；常用方式之一是用稳定的任务标识识别已有结果，但具体办法取决于存储和并发条件。它不是“重试天然安全”的保证。真实文档还必须给出本项目实际采用的办法、相关实现入口及覆盖中断场景的验证证据。

示例说明了三种深度，也说明为什么只写“采用异步架构，提高可维护性”不足以沉淀知识。代码入口帮助代理核验和维护，用户不必打开它才能读懂正文。

## 6. 嵌入开发过程，避免额外文书任务

| 时机 | 动作 | 产出与完成条件 |
| --- | --- | --- |
| 新功能或重要行为变更开始时 | 从已有需求提取用户场景、行为及限制；重要架构取舍补简短说明 | 放入已有任务说明或相关文档的计划部分；范围能用于实现和验收，不要求另写计划文件 |
| 实现与验证中 | 沿用真实发现，修正假设；记录会影响设计或使用的取舍 | 复用当前任务上下文，不逐次记录工具调用或失败尝试 |
| 交付本次变更时 | 对照实际变更与验证更新相关段落；补知识解释及必要链接 | 行为、实现、状态一致，计划不冒充已实现；架构变化才更新总览，功能范围变化才改索引 |

小修复如果没有改变文档描述的行为、机制或重要经验，就不必产生文档差异。修正代码以兑现原本正确的说明时，保留说明即可。无需输出“本轮无需更新文档”的固定报告。

这不是把所有设计都提前冻结。未知机制可先做小实验，验证后再形成说明；探索任务可只交付结论与未知事项，不伪造完整功能文档。

对已有项目，首次补齐全貌可以是一次明确授权的文档任务：先整理总览和功能索引，再按重要性补实现。若用户只要求普通维护，则只核对本次相关文档和实现，不因缺少总览而开始全库扫描，不把局部摸清的情况写成完整全貌。部分覆盖必须在文档中明确说明，不能靠空白表格假装完备。

## 7. 常驻规则应保留什么

建议在选择此文档体系的项目中保留以下短规则。它是待采用文本，不是本次已生效的修改：

> 本项目用“架构—功能—实现”文档支持开发、验收和长期学习，位置为 `doc/架构-功能-实现/`。架构说明整体结构与关键选择，功能说明软件能力和对外行为，实现说明机制、理由、限制及必要的代码与验证入口。
>
> 开发前读取与任务相关的说明；新增功能或重要行为变化时明确预期行为。交付时依据实际实现和验证，同步维护本次影响的文档，并解释值得积累的关键知识。修复后仍符合原说明时无需制造文档改动。
>
> 创建、补齐或实质更新这些文档时，应用已安装的 `architecture-feature-docs` 技能；微小文字修正直接完成。保留用户选择的结构，日常只处理相关部分，不默认重写整库。计划、当前实现和未验证判断必须区分。

安装时必须把技能实际入口加入项目指引，或按目标代理支持的方式配置。仅出现技能名称不保证它能被加载。技能不存在时不声称已使用；仍按规则完成已授权文档工作，并说明缺失。

这段规则解决“什么时候做、做到什么程度”，技能解决“怎样写得可靠且有学习价值”。通用规则包可把它作为明确可选的文档政策；对用户自己的项目，选择后就作为默认工作约定，不必每次询问是否需要文档。

## 8. 技能范围与内部组织

建议一个技能 `architecture-feature-docs`，中文显示名“架构、功能与实现文档”。暂不拆成三个技能，以免共享规则重复、三层内容相互脱节。

入口包含目标、触发条件、三层职责、真实性边界及轻量更新流程。需要的附属材料仅两份：

- `references/document-shapes.md`：各层需要回答的问题与简短示例；创建页面或实质改写时读取。它规范必需信息，不强制八个标题。
- `references/initial-documentation.md`：首次建立完整文档时如何核对覆盖范围、分批补齐及标明未知；日常维护不加载。

不默认创建脚本、术语表、全局台账、评分文件或独立学习卡片。后续真实重复需求出现后再添加工具。clear-communication 负责表达质量，本技能负责文档内容、事实和更新方式；不复制它的完整写作流程，也不因其缺失让文档任务停摆。

### 执行步骤与可检查产出

1. **确定范围和依据。** 从当前任务、相关文档、代码与验证结果确定本次影响的内容。首次全面建档才盘点全貌。产出是需要修改的位置及已有证据，可留在工作上下文，不强制另存清单。
2. **写行为和解释。** 更新对应层次；先写用户能观察到什么，再解释机制和关键选择。不要猜测历史动机：找不到记录时区分“当前机制可以解释的作用”与“当初选择原因未知”。产出是实际文档改动。
3. **核对一致性与阅读效果。** 检查改动涉及的事实、计划状态、关系图、链接及共享说明；确保读者不用读代码即可理解正文。针对缺陷修正后结束，不额外生成逐项自检报告。

完成标准：文档内容有依据，三层关系一致，关键知识解释到足够理解，用户可以找到相关内容；不是“八节齐全”“有来源列表”或“代理说已检查”。

## 9. 验证方案与下一步

先在一个实际功能上验证，再完善技能。需要同时检查事实正确、读者理解和维护成本，而非仅检查文件格式。

| 场景 | 观察结果 |
| --- | --- |
| 从已有实现建立文档 | 功能全貌无重大遗漏；架构与代码一致；未知历史理由未编造 |
| 新功能从计划变成实现 | 计划与现状区分清楚，交付后描述真实行为及限制 |
| 改变跨功能共享机制 | 共享说明更新一次，受影响功能保持一致，无多份矛盾副本 |
| 修复一处小错误 | 不扩大成全库补文档，不给无关页面制造修改 |
| 文档与代码冲突 | 能识别约定和现状差异，依据需求处理，不盲目改代码或改文档 |
| 重要决定被替代 | 当前说明正确，必要历史仍可追溯，不把两种方案并列成现行要求 |
| 不读源码理解设计 | 读者能解释主要部分如何协作、为什么这样选择，以及换个约束后是否仍适用 |

代理事实核验和人类学习验证分开：前者对照源码、测试和文档；后者可邀请用户阅读后用自己的话解释，再隔一段时间回看能否迁移到另一个问题。理解测试只在评测时进行，日常不要求用户答题。不要仅凭代理评价自己的文字，就宣称读者学会了。

对同一组任务比较原规则与新技能的遗漏、事实错误、额外文件、工具调用、token 和耗时；记录模型与环境，重复运行。当前仅完成设计研究，没有这些实验结果。

推荐实施顺序：先确认本方案中的文档职责与默认维护政策；据此建立技能和示例，在真实功能上试用并修正，然后再替换根规则里的长模板。不会因为本次讨论就自动启用候选规则或批量重写已有项目。
