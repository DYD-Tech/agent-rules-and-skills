# 唯一真源与多代理维护

日期：2026-10-28。用户目标是跨项目、跨代理使用同一套不断演进的规则与技能，而不仅是方便复制安装。

## 原方案的问题

已有流程允许保留本地修改，但没有明确谁有权成为标准，可能让每个项目保留不同“改进”。以主要宿主目录作为维护来源也容易误解：它只能是项目内派生文件的位置，不能取代选定仓库的内容权威。浮动外部 main 会让同一个目录版本在不同时间装出不同内容。

## 本次设计

真源维护内容和适配约定；业务项目保存锁定版本的安装结果；项目特有约束独立存放。跨宿主差异必须可追溯，适配不得改变行为；无法无损转换时说明限制。不同物理副本不是问题，无法解释差异、不能重建来源才是问题。

同步比较旧来源、目标来源及本地生成结果。只有上游变化和只有本地变化应分别处理，双方变化不能直接覆盖。上游版本更新后，所有登记的适配结果都要按同一目标重建并检查，未完成的环境标待同步。无需每轮联网；首次安装、添加代理、明确检查更新或准备修改托管内容时才检查。

外部模块由目录指定上游与版本策略，实际安装提交锁入项目记录。track-branch 在首次安装和明确升级时解析远端分支；普通重装与新增 agent 复用已有提交。此策略允许不同安装时间产生不同版本，但差异必须可追溯；跨项目统一版本需授权批次选择同一提交。fork 用户可选择自己的真源；外部自定义源码仍需单独 fork 并调整映射。

## 落地文件与能力边界

- SYNC.md：代理检查、更新、处理偏离和汇回改进的流程。
- adapters/README.md：宿主适配边界和支持证据；没有自动格式转换器。
- catalog/installation-record.md：记录格式，区分源码来源和适配后哈希。
- tools/audit_installation.py：只读检查已安装文件相对记录的变化、缺失和受管目录的额外文件；不联网，不修改，不判断上游最新。

这保留“告诉代理来做”的使用方式，同时将机械的本地偏离检查交给小工具。没有建设后台包管理服务，没有自动扫描其他项目，也没有在普通开发中增加全面同步。
